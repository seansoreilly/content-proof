# Ubiquitous Language

Derived from the README, ADR 0001, the PRD, the user guide, the cryptography
explainer, and the domain code under `src/lib` as of 2026-10-25. No prior
conversation fed this version; re-run `/ubiquitous-language` after a design
discussion to fold in new terms.

## The record and its parts

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Record** | The signed statement that a named Google account submitted a given hash at a given time, plus the signatures over it. | Signature (for the whole thing), signature record, proof, certificate, stamp, receipt |
| **Statement** | The UTF-8 string `<hash_hex>:<email>:<timestamp>` that the account holder signs and that a version 2 record's service signature covers. | Signed message, message, data to sign |
| **Countersigned statement** | The statement extended with the account holder's key and signature, which the service signature covers in a version 3 record. | Service message, v3 message |
| **Hash** | The SHA-256 digest of the file, hex in the statement and base64url in the payload. | Fingerprint, digest, checksum |
| **Timestamp** | The time named in the statement, in milliseconds since the Unix epoch, chosen by the browser for version 3 (within a server-checked skew window) and by the service for version 2. | Issued at, signed at, date, server time |
| **Service signature** | The Ed25519 signature by the service key over the statement or countersigned statement; it also serves as the record's lookup key. | Signature (unqualified), s, sig |
| **Account holder signature** | The Ed25519 signature by the account holder key over the statement, present only in version 3 records. | User signature, usig, us |
| **Record version** | The format number leading the payload: 2 for service attestation only, 3 for account holder signature plus countersignature. | Format version, payload version |
| **Version 2 record** | A record carrying only the service signature, issued when the browser cannot hold an Ed25519 key. | Service-only record, fallback record, basic record |
| **Version 3 record** | A record carrying the account holder signature and the service countersignature over it. | User-signed record, countersigned record, full record |
| **Legacy record** | A record from before the tilde format, carried as base64url JSON in a `?data=` query string, accepted only when its key is a published key. | Older record, old QR, v1 |
| **Payload** | The tilde-separated, URL-safe encoding of a record that travels in the verification URL fragment. | Record (when the string is meant), QR data, token |
| **Verification URL** | The `https://<host>/verify#P=<payload>` link that opens the verifier with the payload never reaching the server. | QR link, verify link, share URL |
| **QR code** | The image that encodes a verification URL. | Signature, proof, badge, seal |

## Keys and signing parties

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Service** | ContentProof itself, the party that checks sign-in and signs or countersigns every record. | Server, backend, notary, authority |
| **Service key** | The Ed25519 keypair held by the service, whose public half is published in the key set. | ContentProof key, signing key, master key |
| **Key id** | The first 16 characters of base64url(SHA-256(SPKI DER)) of a service public key, naming which service key signed a record. | kid, keyId, key identifier, pk |
| **Key set** | The published document at `/.well-known/public-keys.json` listing current and previous service public keys by key id. | Keyset, key document, public keys JSON, JWKS |
| **Key rotation** | Replacing the current service key while keeping the old public key in the key set so existing records still verify. | Key rollover, re-keying |
| **Account holder** | The person behind the Google account whose email a record names. | User, signer, signee, owner, author, creator |
| **Account holder key** | A non-extractable Ed25519 keypair generated by WebCrypto in the account holder's browser and kept in IndexedDB, one per browser profile. | User key, ukey, browser key, personal key, device key |
| **Key binding** | The service's assertion, made when it countersigns, that an account holder key was presented in a session signed in as that account. | Key ownership, identity binding, trust |
| **Session** | The signed-in Google identity on which the service decides whose email goes into a record. | Login, account, auth |

## Verification

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Attestation** | What any valid record proves: the service vouches that the named account submitted the hash at the timestamp. | Proof, certification, notarisation, authentication |
| **Non-repudiation** | What a version 3 record adds: whoever held the account holder key approved exactly this statement. | User proof, ownership proof, authorship |
| **Verifier** | Whoever checks a record against the key set, usually the in-browser verify page, which also works offline once the key set is cached. | Validator, checker, scanner |
| **Verification** | Recomputing the hash, rebuilding the statement, and checking each signature against its key. | Validation, authentication, proof |
| **Verification failure** | The single reason a record does not verify: unknown key, hash mismatch, bad signature, bad account holder signature, or malformed. | Error, invalid, rejection |
| **Submitted hash** | The hash a record names, as distinct from the hash of the file the verifier is holding. | Original hash, expected hash |

## Transparency log

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Transparency log** | The append-only sequence of every issued record, over which a Merkle tree is built. | Audit log, ledger, history, record log |
| **Log entry** | One record in the transparency log, identified by its index. | Leaf, row, item |
| **Leaf hash** | SHA-256 of `0x00` followed by the encoded record, per RFC 6962. | Entry hash, record hash |
| **Root** | The Merkle tree hash over all log entries at a given size. | Tree hash, top hash, Merkle root |
| **Log head** | The signed tuple of log size, root, timestamp, and key id that the service publishes at `/api/log/head`. | Tree head, signed tree head, STH, checkpoint |
| **Inclusion proof** | The audit path from a leaf hash to a root, showing that a record is in the log at a given size. | Proof (unqualified), Merkle proof, audit path |
| **Archived log head** | A log head stored somewhere the service does not control, so later heads can be checked against it. | Witness, snapshot, backup, mirror |
| **Log mirror** | A copy of all log entries fetched by an auditor to recompute the root independently. | Archive, dump, export |
| **Record store** | The optional keyed store that returns a record by its service signature for `/sig/<signature>`. | Database, log (it is not the log), cache |

## Relationships

- A **Record** names exactly one **Account holder** (by email), one **Hash**, one **Timestamp**, and one **Key id**.
- Every **Record** carries one **Service signature**; a **Version 3 record** also carries one **Account holder signature** and one **Account holder key**.
- A **Version 2 record** has its **Service signature** over the **Statement**; a **Version 3 record** has it over the **Countersigned statement**.
- One **Payload** encodes exactly one **Record**; one **Verification URL** carries exactly one **Payload**; one **QR code** encodes exactly one **Verification URL**.
- A **Key id** resolves to at most one entry in the **Key set**; a record whose key id is absent fails with an unknown-key **Verification failure**.
- An **Account holder** may have many **Account holder keys** (one per browser profile); each **Version 3 record** names the one that signed it.
- **Key binding** is asserted by the **Service**, not proven by the record; publishing the **Account holder key** elsewhere gives verifiers an independent binding.
- Every issued **Record** becomes one **Log entry**; the **Transparency log** has many entries and one **Root** per size.
- A **Log head** covers all **Log entries** up to its size; an **Inclusion proof** ties one **Log entry** to one **Root**.
- An **Inclusion proof** is only meaningful against a **Log head** of the same size, and a **Log head** only constrains the **Service** once it is an **Archived log head**.
- The **Record store** and the **Transparency log** both live in Redis but are separate structures; only the log is append-only.

## Example dialogue

> **Dev:** "A verifier scans a **QR code** and ends up on the verify page. What exactly has it got at that point?"

> **Domain expert:** "A **Verification URL**. The part after `#P=` is the **Payload**, a tilde-separated string the browser decodes into a **Record**. The server never sees it."

> **Dev:** "The record has two signatures. Which one is whose?"

> **Domain expert:** "The **Service signature** is always there and is made with the **Service key** named by the **Key id**. In a **Version 3 record** there is also an **Account holder signature**, made with the **Account holder key** that lives in that person's browser. The service signs over the **Countersigned statement**, which includes the account holder's key and signature, so you check both."

> **Dev:** "And if both check out, is that proof the account holder made the file?"

> **Domain expert:** "No. It is **Attestation** that this account submitted this **Hash** at this **Timestamp**, plus **Non-repudiation** that the holder of that key approved the **Statement**. **Key binding** between the key and the email is the service's claim. Authorship is never in scope."

> **Dev:** "The page then fetches an **Inclusion proof**. If that fails, is the record invalid?"

> **Domain expert:** "No. The record's validity comes from the signatures. The inclusion proof plus a **Log head** of the same size shows the record is in the **Transparency log**, so the service cannot later deny or back-date it. A failed inclusion proof means distrust the log, not the record. And the log head only binds the service once someone holds an **Archived log head**."

> **Dev:** "Last one: `/sig/<signature>` takes a signature. Which signature?"

> **Domain expert:** "The **Service signature**. It doubles as the record's lookup key in the **Record store**, which is a convenience and not the log. A record is complete without it."

## Flagged ambiguities

- **"Signature" means three things.** It names the service's field, the account holder's field, and the whole record (routes `/sig/<signature>`, the PRD's `SignatureData`, analytics event names). Use **Record** for the whole, and qualify the two fields as **Service signature** and **Account holder signature**. Where the service signature is used as a lookup key, say so.
- **One person, three names.** Code says "user" (`userKey`, `userSigned`, `RECORD_VERSION_USER_SIGNED`), ADR 0001 and the README say "account holder", the verify page and user guide say "signer". Use **Account holder**. "Signer" is misleading because the service also signs; keep "user" as a code-only alias and do not use it in copy or docs.
- **"Proof" is overloaded.** It is half the product name, the PRD's marketing frame ("cryptographic proof"), and the Merkle audit path. Reserve **Inclusion proof** for the audit path. Avoid bare "proof" for what a record gives, since the product's own docs say it is not proof of authorship; say **Attestation** or **Non-repudiation** as appropriate.
- **Hash, fingerprint, digest.** The upload component says "fingerprint", the explainer says "digest", code and README say "hash". Use **Hash** everywhere. Note the two encodings: hex in the statement, base64url in the payload.
- **Log head versus tree head.** The endpoint and type say log head; the README and RFC 6962 say tree head. Use **Log head**. "Tree head" is acceptable only when quoting the RFC.
- **Key set, keyset, key document.** Three spellings for the file at `/.well-known/public-keys.json`. Use **Key set**.
- **Key id, kid, keyId, pk.** Use **Key id** in prose; `k` and `kid` are wire-format names and `pk` is a dead PRD field.
- **Version 2 and version 3 need plain-language names.** The verifier reports which it saw. Say **Version 2 record (service attestation only)** and **Version 3 record (account holder signature plus countersignature)** on first use; do not invent "basic" or "full".
- **"Older records" versus legacy.** The verify page says "older records" for the `?data=` JSON format. Use **Legacy record** so it is not confused with a version 2 record, which is current but service-only.
- **Record store is not the log.** Both are in Redis and both hold records, so "the store" and "the log" get swapped. The **Transparency log** is append-only with a Merkle tree; the **Record store** is an optional lookup by service signature.
- **Stale PRD terms.** The PRD describes a trust level (basic/enhanced/premium), a UUID `id` field, a `pk` identifier, ISO 8601 timestamps, and a 10 MB limit. None of these shipped. Its JSON payload shipped only as the `?data=` form that is now the **Legacy record**. These are not aliases; they are superseded. Treat the README and ADR 0001 as current.
- **Product name spelling.** Both "ContentProof" and "Content Proof" are used (README versus page titles and user guide). Pick one; this glossary uses **ContentProof** because that is how the code, README, and ADR write it.
- **README opening claim.** "You hold no key" describes version 2 only and contradicts version 3. The sentence should say the service key is not the account holder's key, and point to the version 3 section.
